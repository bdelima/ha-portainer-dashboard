# Portainer Maintenance

A Home Assistant custom integration that turns the core [`portainer`](https://www.home-assistant.io/integrations/portainer/) integration into a full review-and-approve maintenance workflow for container updates, container health, and stale-device cleanup — built on top of a companion notification/automation design. See the [full design doc](https://github.com/bdelima/ha-portainer-dashboard/blob/main/docs/portainer-ha-container-management-design.md) for the whole system this integration is one piece of.

On setup, this integration:

- Registers `portainer_maintenance.remove_device` — a real service for deleting stale Portainer devices/stacks that HA's own UI can't delete via any documented service (built on the stable `device_registry.async_remove_device()` API).
  - *(unreleased)* **Stale Devices say what kind of device it is.** The line under each name used to read "Stale — no longer in Portainer" for a stack, a container and a volume alike. It now names the type and ends "no longer exists in Portainer": "Stack …", "Volume …", "Container …" (a container directly under the endpoint, or whose stack can't be determined), and for a container inside a stack, "Container in stale stack *x* …" (the stack is on the list too), "Container in running stack *x* …" or "Container in stopped stack *x* …" (the stack still exists; running or stopped is read from its stack switch). The host name is left out of the line because the item's name already ends with it. Core's Portainer integration has no network devices, so only stacks, containers and volumes can go stale.
- Registers `portainer_maintenance.prune_images` — reclaims disk space by pruning Docker images across every Portainer endpoint this HA instance knows about, discovered automatically from the device registry (no static host list to maintain), or limited to specific endpoint(s) via an optional `device_ids` field *(1.3.0)* — used by the webapp's Cleanup tab, where a single tree row targets one host rather than every host.
- Registers `portainer_maintenance.prune_volumes` *(1.3.0, new)* — reclaims disk space by pruning unused Docker volumes, the same way and with the same `device_ids` scoping as `prune_images`. Core's own `portainer` integration has no dedicated service for this, only a `button.*_volumes_prune` entity per endpoint (the same action Portainer's own "Prune unused volumes" button performs), so this wraps that button via HA's standard `button.press` rather than duplicating core's pruning logic. Offered as a courtesy on the Cleanup tab — core's own volume entities give limited visibility into what's actually unused, so treat this as "the same button Portainer's UI has," not a more informed decision.
- Registers `portainer_maintenance.reload_endpoint` *(1.3.0)* — reloads the core `portainer` config entry that owns a given device, the same reload Settings → Devices & Services → Portainer → Reload performs. Exists because core's own integration silently drops an endpoint from its data the moment it can't reach it — no error, no dedicated "endpoint unavailable" entity anywhere — which `sensor.portainer_trouble` now surfaces as an actionable item instead of something you'd only notice by accident.
- `prune_images` and `prune_volumes` both nudge the relevant Home Assistant entities to refresh a few seconds after acting *(1.3.0)*, since core's own `portainer.prune_images` service doesn't call a coordinator refresh itself the way its button/switch entities do — without this, a Cleanup tab badge could sit stale for up to core's own next 5-minute poll.
- Registers `portainer_maintenance.perform_update` and `portainer_maintenance.update_done` — native services (not user-created scripts) for actually installing an update and posting the "update performed" confirmation, notifying whichever mobile_app device(s) you pick during setup. These used to be separate script blueprints requiring you to manually set each script's Entity ID to match what the automation blueprint called by name — an easy step to get wrong, which HA would then report as a cryptic "automation uses an unknown action" error. A native service has no such step to miss.
  - (1.2.6) Fixed both push notifications ("Update performed: ...", "Stack restart needed: ...") reading the update entity's own `friendly_name` (e.g. "trawl Image update available") into the notification title instead of the container's real name — the same bug class fixed for the dashboard's item list back in 1.2.2, just in this separate code path (`handle_perform_update`'s own device-name lookup), which that earlier fix never touched.
  - *(1.3.0)* The stack-restart-needed push is now purely informational — it no longer carries an inline "Restart Stack Now" action. A stack can have several independent per-container update notifications in flight at once, and a one-tap restart baked into any one of them made that workflow feel disconnected from the others; the remediation now lives only on the dashboard's Trouble tab, and this notification's tap action opens the dashboard directly on that tab instead. Every notification this integration sends also now carries an explicit no-op **Dismiss** action alongside whatever real action(s) it has.
- Installs its own bundled automation blueprint into your Home Assistant config automatically — no manual file copying.
  - *(1.3.3)* The bundled blueprint's four notification categories (Updates, Trouble, Stale Devices) each now expose their own Android notification channel name (a `select` input, defaulting to `"Portainer Updates"`/`"Portainer Trouble"`/`"Portainer Stale Devices"` — editable, and each customizable afterward in your phone's own notification settings: sound, importance, lock-screen visibility) plus an independent **Bypass Do Not Disturb** toggle, off by default. Previously, Trouble unconditionally used `channel: alarm_stream` with `priority: high`/`ttl: 0` — a reserved, phone-wide Android channel that plays at alarm volume and bypasses silent mode/Do Not Disturb the same way a phone alarm clock does — which meant *any* trouble item (even one that could obviously wait) rang like an alarm, at any hour. See [issue #1](https://github.com/bdelima/ha-portainer-dashboard/issues/1). Reconfigure an existing automation (Settings → Automations & Scenes → the Portainer Maintenance automation → Edit → the blueprint's own settings) to pick up the new inputs; nothing changes automatically for an already-configured automation beyond what you explicitly opt into. No effect on iOS notifications (Android-only concept) — not something this integration has users for yet.
  - *(1.3.4)* Updates, Trouble, and Stale Devices all push to a phone on a rising count; a rising dangling-image count never did. Added a fifth notification category, **Cleanup**, mirroring the Stale Devices shape exactly — its own `cleanup_channel` name input (default `"Portainer Cleanup"`) and `cleanup_bypass_dnd` toggle, firing only when `sensor.portainer_cleanup` increases, never on the count just dropping after a prune. Its notification links to the dashboard's Cleanup tab via `#cleanup`. No existing category's behavior changed.
  - *(1.3.5)* The Trouble notification's `clickAction`/`url` now link to `#needs-remediation` instead of `#trouble`, matching the sidecar webapp's Trouble tab display rename to "Needs Remediation" (its 1.3.11). The sensor entity (`sensor.portainer_trouble`) and this blueprint's trigger id (`container_trouble`) are unchanged — only the URL fragment the notification deep-links to moved. Requires sidecar 1.3.12 or later, which aliases `#needs-remediation` onto its existing `trouble` tab; an older sidecar simply won't recognize the new hash and will open on whichever tab was last active, the same as any unrecognized fragment.
  - *(1.3.6)* The one-time "Portainer Maintenance: one more step" notification shown right after setup — the prompt to actually create an automation from this bundled blueprint — used to link to `/config/automations/dashboard` (plural). That's not a real Home Assistant frontend route (the config routes are singular: `/config/automation`, `/config/blueprint`), so tapping it opened a blank page instead of anywhere useful. It now links to `/config/blueprint/dashboard` — a real route — and tells you to click the "Portainer Maintenance" row there, which opens the automation editor already pre-filled with this blueprint. There's no supported way to open that editor pre-filled directly from a URL (Home Assistant passes that handoff through in-memory frontend state, not a link), so the Blueprints page is still the closest one-click path. A notification already created by an older version keeps its old dead link until dismissed — create a new one from Settings → Devices & Services → Portainer Maintenance → ⋮ → **Reconfigure** if you want the fixed link, or just go straight to Settings → Automations & Scenes → Blueprints → "Portainer Maintenance".
  - *(unreleased)* **Daily reminder.** An update-available push fires once per newly-appeared update (plus once at startup), so an update left alone was never mentioned again. The blueprint now has two inputs, **Updates -- Daily Reminder** (on by default) and **Updates -- Reminder Time** (09:00 by default): while at least one update is still pending, it sends one "Updates still pending" push a day at that time on the Updates channel, using the same notification tag as the other update pushes so it replaces them in the tray instead of stacking. It is a time of day rather than an interval because a blueprint has nowhere to keep "when did I last remind". Existing automations pick up the two inputs with their defaults, so the reminder starts on its own; turn it off in the automation's blueprint settings.
  - *(unreleased)* The blueprint keeps **50 traces** of the automation (Home Assistant's default is 5). Every trigger runs this one automation, so a handful of unrelated runs pushed out the one you were looking at. After updating, restart Home Assistant and run `automation.reload` (or restart a second time) so the already-loaded automation picks it up.
- Registers a sidebar panel (iframe) pointing at your own Portainer-actions webapp, at a fixed path — no dashboard-title guesswork.
  - **Administrators only** (setup / Reconfigure option, **on by default**, including for installs that predate the option): registers the panel as admin-only, the same flag HACS uses for its own sidebar entry, so non-administrator Home Assistant users don't see it. Home Assistant's Settings → Dashboards page only lists its built-in panels and dashboards you create, so an integration's panel can't be switched there — this option is the place to do it. It only hides the panel inside Home Assistant; who can open the webapp's own URL is decided by the webapp's sign-in (next bullet), not by this option.
  - **Sidecar sign-in** *(unreleased)* (setup / Reconfigure): the webapp can now have a login of its own (`AUTH_USERNAME` and `AUTH_PASSWORD` in its compose file, optional; see its README). The form has a **Sidecar allows anonymous access** switch, **on by default** to match the sidecar, which stays open unless you give it credentials. Untick it and a second screen asks for the same username and password (the password field has a show/hide control); the panel's URL then gets an `?auth=<token>` that the webapp trades for a session, so the panel signs in by itself. The token is an HMAC of the username keyed with the password: it is not the password, but anyone who can open the panel in Home Assistant can read it from the page and use it to sign in to the webapp directly, from any browser, until the password changes, so leave **Administrators only** on. With anonymous ticked, no credentials are stored or sent. The password is kept in this integration's config entry in plain text, like any integration credential. Home Assistant forms can't hide fields based on another field, hence the separate screen. An entry created before this option behaves as anonymous. Needs the matching sidecar release; the credentials here must equal the sidecar's, or the panel shows its sign-in page.
- Computes the notification click-through URL automatically as a relative path, which the HA companion app opens inside the app itself — no dependency on HA's own external/internal URL (Settings → System → Network) being configured at all. `#trouble` appended to that path lands the webapp directly on its Trouble tab (as of 1.3.5, the Trouble notification itself instead appends `#needs-remediation` — see above).
- Exposes four native tracking sensors — `sensor.portainer_updates_pending`, `sensor.portainer_trouble`, `sensor.portainer_stale_devices`, and `sensor.portainer_cleanup` — replacing what used to be hand-maintained YAML template sensors.
  - *(1.3.0, breaking rename)* `sensor.portainer_trouble` was `sensor.portainer_container_trouble` — renamed when it grew to cover Portainer endpoints going unavailable, not just individual containers, and containers stuck on a known Portainer/Docker recreate limitation (see below). If anything of yours references the old entity_id by name (a Lovelace card, another automation), update it to `sensor.portainer_trouble`.
  - `sensor.portainer_trouble` now also reports: (1) an endpoint that's dropped out of core's own coordinator data entirely — every entity on that device goes `unavailable` with no error and no dedicated signal of its own; the item carries the endpoint's device_id for a Reload Endpoint action. (2) A container stuck on the confirmed, unfixed Portainer bug where recreating a container sharing another container's network (`network_mode: service:<other>`/`container:<other>`, e.g. a VPN sidecar like gluetun) fails at the Docker daemon level — detected by the same "image reference degraded to a bare digest instead of a normal tag" signal `perform_update` already used internally, now run continuously so it's discoverable at any time, not just in the few minutes right after the update that caused it, and so it survives an HA/integration restart with no special handling needed (the check is stateless, re-derived from live entity state every poll). When the stuck container is part of a real Portainer stack, the item carries a Restart Stack Now action; when it isn't (most likely a Docker Compose project Portainer doesn't manage), it's info-only, since there's no stack for this integration to restart.
  - *(unreleased)* `sensor.portainer_trouble` has a `dismissed_items` attribute next to `items`: what you have dismissed (kind, name, host, `dismiss_key`, `dismissed_at`) that would otherwise be showing right now, so a hidden item is not invisible. A dismissed item whose condition has cleared is not listed, and dismissed items still do not count toward the sensor's state.
  - `sensor.portainer_cleanup` *(1.3.0, new)* — one item per Portainer endpoint, backing the webapp's Cleanup tab. There's no accurate per-endpoint dangling-image count available anywhere in HA's own entities (core's `image_disk_usage_reclaimable` sensor gives a byte-accurate total, but across *all* unused images together, dangling or not, with no way to split it). What each item carries instead is `images_count` minus `containers_count` from core's own per-endpoint diagnostic sensors — a rough "how many images exist beyond what's currently running" estimate, not a precise count, good enough to seed a badge and give a sense of scale — plus the real byte-accurate `reclaimable_mib` figure (omitted, not shown as zero, when that sensor reads `unknown`/`unavailable`, which has been observed inconsistently across endpoints). The sensor's own state is the sum of the estimate across every endpoint, not an item count.
    - *(unreleased)* **Unknown means 0 for the size sensors, and unavailable is flagged.** Core reports `unknown` for the reclaimable size when nothing can be reclaimed and for the volume size when there are no volumes, so `reclaimable_mib` and `volume_usage_mib` are `0` for `unknown`. `unavailable` still gives `None` and sets `reclaimable_unavailable: true`, which makes the webapp disable the image prune (the state is not known). The count sensors still give `None` for both. Each item also carries `refreshed_at` (UTC, set once per refresh of this sensor); the webapp counts distinct values so that an image count that disagrees with a reclaimable size of 0 gets two refreshes to settle before the prune button is enabled.
    - *(unreleased)* **The volume entities are now found.** The volume size sensor and the volume prune button were looked up by entity_id endings (`_volume_disk_usage_total_size`, `_volumes_prune`) that core does not generate (its names give `_volume_disk_usage_total` and `_prune_unused_volumes`), so both were always missing: `volume_usage_mib` was always `None` and `prune_volumes` found nothing to press. Every per-endpoint entity (images count, containers count, reclaimable size, volume size, volume prune button) is now matched on its registry `translation_key` first, with the old suffixes as the fallback. **Prune unused volumes therefore does something for the first time**; the item's `volumes_prune_button` shows which entity it will press.
    - *(1.3.1)* `prune_images`/`prune_volumes`'s post-action refresh nudge used to only ask core's own Portainer diagnostic sensors to refresh from Portainer's API — it never told this integration's own `PortainerCleanupCoordinator` to recompute from those refreshed numbers, and that coordinator otherwise only polls every 5 minutes on its own. The Cleanup tab's count could sit unchanged for up to 5 minutes after an action had already finished and its button had already re-enabled, which read as the action having silently done nothing. Both services now also request an immediate refresh of the cleanup coordinator itself as part of the same nudge, and the sidecar's HTTP call waits for it, so the button staying "busy" now actually tracks how long it takes for the tab's own numbers to catch up.
- Keeps a native HA notification (the bell icon at the top of the sidebar) up to date with a running total across all four sensors whenever anything needs attention, and dismisses it once everything's clear — a real badge/count indicator with no third-party sidebar plugin needed.
- Registers `portainer_maintenance.hide_update_entities` and calls it automatically (at startup, and whenever a new Portainer `update.*` entity is created) — hides that entity from HA's own entity list so it doesn't clutter Settings, since its actual pending/not-pending state is meant to be reviewed on the dashboard instead. Closes what used to be a manual "remember to hide it" step for every new container.
- Registers `portainer_maintenance.update_portainer` — updates Portainer's own server or agent, which `perform_update` refuses (recreating Portainer from inside Portainer stops it before the replacement starts). It starts Portainer's own `portainer/portainer-updater` helper container on the same host, with the Docker socket mounted, running `portainer --image=<ref>` (server) or `agent <schedule id> <ref>` (agent), where `<ref>` is the image reference the container currently runs. The helper is `portainer/portainer-updater` tagged with the version Portainer reports it is running now (one read of the Portainer API's `system/status`; for the agent that is the server's version, which agents are meant to match), never `:latest`, whose Docker Hub tag stopped moving in 2024. If that version can't be read cleanly, nothing is started and the error tells you to update by hand (Portainer's own update prompt, or pull the image and recreate the container). The helper pulls the image, replaces the container with the same configuration, and removes itself when it finishes. For a server container that has a Docker health status of its own (core then shows a health sensor on its device), `--health-check` is added: the helper waits for the new Portainer to report healthy and, if it does not (or does not start), rolls the Portainer database back and restarts the old container; that wait can be long (the updater retries for up to a few hours), during which Portainer is down. Without a Docker health status the flag is left off, because the check it enables can never pass on some Portainer builds and then rolls back an update that worked; the helper still restarts the old container if the new one fails to start. The service returns as soon as the helper has started and does not wait: Portainer is unavailable while it restarts. The container's image needs an explicit tag (a bare digest, a digest pin or no tag is refused). The Portainer API user must be able to create a container that bind-mounts `/var/run/docker.sock` on that host. `dry_run: true` returns what would be run without starting anything (it does read the Portainer version once). It runs only when asked (the webapp's Update now button, or the action called directly); nothing calls it automatically. Not verified against a live Portainer yet: try the agent on a non-critical host first.
  - *(unreleased)* **The dashboard follows the update.** After the helper starts, `sensor.portainer_trouble` follows it (in memory only: a Home Assistant restart forgets it and the row is the plain "Update available" again). The item gets `update_state: "updating"` and `update_now: false`, so the webapp shows "Updating…" and no button, and `secondary_info` says only what has been observed: "Updater started HH:MM", then "Portainer is restarting" (core's Portainer data is not refreshing, or the update entity is unavailable), then "Updated, waiting for Home Assistant to confirm" (Portainer's container id under the same name has changed and, for a start with `--health-check`, the helper container is also gone from core's container list; core's update entity turns off a little later, on its own refresh, which is the lingering row seen before). Nothing is inferred: the verdict comes from the new container id, the helper disappearing from core's list, Portainer being reachable, and the clock. **Failed** is one of: the helper is gone (seen on two separate core refreshes) while Portainer still runs its old container id; or no verdict within the ceiling -- 5 minutes after the helper started, or about 3 hours when `--health-check` was passed (the updater retries that check for about 2.75 hours, plus up to 5 minutes for a database rollback). The item then returns as `update_state: "failed"` with the reason in `secondary_info`, the manual steps in `detail`, no Update now button, and Dismiss. The Trouble sensor refreshes every 10 seconds while an update is followed (a minute otherwise), and `update_portainer` asks for a refresh as soon as the helper starts. The repeat guard (10 minutes) is now keyed on the update entity instead of the container id, which changes when an update works, and a start is refused while the update is still being followed.
  - *(unreleased)* **`update_now` is computed.** It used to be `true` on every Portainer self-update item. It is now `true` only when the container's image has a usable tag and Portainer's version can be read as a plain `x.y.z` (one `system/status` request per Trouble refresh while a Portainer update is pending, cut off after 5 seconds). Otherwise the item has no Update now button, and its More Info says the container is in a state that doesn't allow programmatic updates, with the manual steps (`docker compose pull && docker compose up -d` in the compose file's directory). Both More Info texts, and the agent's (the same with "Portainer agent" as the subject), end with a note that Portainer is briefly unavailable while it restarts, so other update and cleanup actions will not work until it is back. `perform_update` still refuses Portainer's own containers, and now points at `update_portainer`.
- Attaches a `changelog_url` to each item in `sensor.portainer_updates_pending` when one can be found, surfaced by the webapp as a "Changelog" link next to Install, always pointed at the project's GitHub *Releases* page rather than its repo home page. A small hand-curated table covers a few pinned images directly; everything else is resolved automatically, tried in order: (1) reading the image's own `org.opencontainers.image.source` OCI label straight off its registry manifest (Docker Hub and `ghcr.io` only, anonymous/public access, no credentials involved) — the authoritative answer for any image that sets it, and the only method that correctly handles a monorepo publishing more than one differently-named image (no naming relationship to guess from at all); (2) for an image that doesn't set the label, a direct owner/repo guess against GitHub (right for any project, self-published images included, whose Docker Hub namespace and repo name match its GitHub owner/repo exactly), tried for both `ghcr.io` and Docker Hub/`lscr.io` images; (3) falling back to scanning the Docker Hub listing's README text for a GitHub link only when the guess doesn't resolve either (needed for a project like linuxserver.io, whose GitHub repos are named `docker-<app>` rather than `<app>`). Every guessed/scraped/labeled URL is verified live before it's used, and the result cached so this only costs network round trips once per image ever seen with a pending update.
  - (1.2.5) Added the OCI-label discovery method above — fixes changelog discovery for a monorepo that publishes multiple images under different Docker Hub names (e.g. `bdelima/immich-display-integrations`, which publishes both `bdelima/immich-overflight-feed` and `bdelima/immich-frame-mirror` from two subfolders of one repo), for any image built with `org.opencontainers.image.source` set — see the `local-build-pipeline` project skill's OCI-label bootstrap step, which every new image should set going forward regardless of whether this integration is tracking it.
  - (1.2.4) Fixed a bug where changelog discovery (and the update-recreate outcome check in `__init__.py`) could silently never run at all for a container. Home Assistant entity IDs are unique globally, not per device — running the same-named service on more than one host (e.g. the same exporter on two hosts) means both containers' image sensors want the same object_id, and the registry auto-suffixes the second one (`..._image_2`) on whichever host lost that naming race. The image-entity lookup used to match only a bare `..._image` suffix, so it silently found nothing for the suffixed host and bailed out before logging anything — now it matches either suffix shape.
  - *(1.3.2)* Also attaches a `changelog_repo` field — the bare `owner/repo` pulled back out of `changelog_url` when it's a github.com URL, `None` otherwise (a non-github.com override, or no changelog found at all). Exists so the sidecar webapp can fetch a repo's release notes via GitHub's own API and render them in-app instead of linking out to `changelog_url` — which, across three separate attempts (see the sidecar's own README changelog), turned out to have no working fix from inside Home Assistant's companion app: its embedded webview won't open a new window for a `target="_blank"` link, and any same-window fallback can only navigate the sidecar's own iframe, breaking the panel when the destination (correctly) refuses to be framed. `changelog_url` is unchanged and still present, for anyone running an older sidecar version or one that still wants a plain link.
  - **Overriding a changelog link without a new release:** drop a JSON file named `portainer_maintenance_changelog_overrides.json` in your Home Assistant config directory (the same folder as `configuration.yaml`) with entries shaped `{"owner/repo-path": "https://..."}`, keyed by the image's repo path exactly as it appears in the image reference (no registry host, tag, or digest — e.g. `qmcgaw/gluetun`, not `ghcr.io/qmcgaw/gluetun:latest`). This file always wins over the integration's own built-in table when both have an entry for the same image, and is re-read on the next 5-minute poll — no HA restart, no new integration version. Example:
    ```json
    {
      "myorg/myimage": "https://github.com/myorg/myimage/releases",
      "someowner/some-fork": "https://github.com/someowner/some-fork/releases"
    }
    ```

## Requirements

- **Home Assistant 2026.10 or later.** An update is listed on the dashboard exactly while the core `portainer` integration's own update entity reports one, with no "recently installed" hold of this integration's own in between. That relies on core's fix ([home-assistant/core#182648](https://github.com/home-assistant/core/pull/182648)) that re-checks a recreated container's image straight away, which first shipped in 2026.10.0. On older versions an installed update can keep showing as pending, and older versions have also been observed to fail during setup.
- **Home Assistant Container Edition only.** This integration has only been run and tested against a Container Edition install; it has not been verified against Home Assistant OS or Supervised, and setup steps that assume shell/filesystem access at the container level may not carry over cleanly to those install methods.
- Home Assistant with the core `portainer` integration already configured against at least one Portainer endpoint.
- The [Portainer Sidecar](https://github.com/bdelima/ha-portainer-sidecar) webapp, running as its own Docker container and reachable from Home Assistant — this integration only points a sidebar panel at its URL, it doesn't build, run, or provide that container itself. A prebuilt multi-arch image is published to Docker Hub as [`bdelima/ha-portainer-sidecar`](https://hub.docker.com/r/bdelima/ha-portainer-sidecar) (`docker pull bdelima/ha-portainer-sidecar:latest`); see that repo's README for Compose and `docker run` examples, or to build it from source instead.

## Installation via HACS

1. HACS → the "⋮" menu (top right) → **Custom repositories**.
2. Repository: `https://github.com/bdelima/ha-portainer-dashboard`, Category: **Integration**.
3. Find **Portainer Maintenance** in HACS → Integrations → **+ Explore & Download Repositories**, install it.
4. **Restart Home Assistant** — new `custom_components` are only loaded at startup.
5. Settings → Devices & Services → **Add Integration** → search "Portainer Maintenance" → enter your webapp's URL and pick the mobile_app device(s) that should get the "update performed" confirmation push. **Sidecar allows anonymous access** is ticked by default, which is right unless you gave the sidecar container an `AUTH_USERNAME` and `AUTH_PASSWORD`. If you did, untick it and the next screen asks for that username and password.
6. Settings → Automations & Scenes → Create Automation → **Use Blueprint** → "Portainer Maintenance: automations (merged)" → pick your notify device(s) (can be the same ones as step 5, or different).

Already on an older version and don't see the notify-device field from step 5? Settings → Devices & Services → Portainer Maintenance → ⋮ → **Reconfigure** adds it to your existing setup without deleting and re-adding the integration.

## Manual installation (without HACS)

Copy `custom_components/portainer_maintenance/` into your Home Assistant config's `custom_components/` directory, then follow steps 4–6 above.
